# Market Regime Detection System

[![Tests](https://github.com/Anshuman0716/Stock-Market-Regime-Prediction/actions/workflows/tests.yml/badge.svg)](https://github.com/Anshuman0716/Stock-Market-Regime-Prediction/actions/workflows/tests.yml)

**A quantitative data science & risk project**

This project labels each trading day as **Bull, Transition or Crisis** using a 4-state Gaussian Hidden Markov Model (HMM) trained on 8 technical and macro features. It then tests whether moving in and out of the market based on those labels beats simple baselines (buy-and-hold, a 200-day moving average and volatility targeting) after trading costs, trading real funds (SPY, ONEQ, GLD) and Bitcoin, with idle cash earning the T-bill rate.

The project's priority is an **honest evaluation**: no look-ahead bias anywhere in the pipeline, strictly out-of-sample results, the same costs and execution lag for every strategy, and statistical tests that correct for multiple comparisons.

### Why Gold looked worse in Step 7, and the fix (Step 8)

After Step 7 gave Gold a Transition regime, Gold's HMM Sharpe fell. The cause was **sizing, not labeling**. The strategy used to hold smoothed P(Bull) of the asset, so Transition was treated exactly like Crisis: as cash. Gold's Transition regime is a quiet drift that earned a positive return in its training windows and kept earning one out-of-sample, so sitting in cash through it gave that return away.

**The fix:** each regime now gets a weight from its **training** window: 100% if the asset's mean return on that regime's training days was positive, otherwise 0%. Exposure = Σ P(regime) × weight. Crisis was never held in any fold for any asset. Transition is held in the folds where it earned money in training: most of Gold's and some of the S&P 500's and NASDAQ's.

**The trade-off:** Gold's Sharpe improves. On the stock indices, holding Transition adds growth (higher CAGR) but adds risk faster than return, because their Transition days have a much lower return-to-risk ratio than the Bull days the strategy already held, so their Sharpe dips slightly and their worst drawdown deepens: NASDAQ's went from −22.7% to −37.7%, now deeper than buy-and-hold's (see the table above). A side effect: holding the market more of the time makes the HMM's daily returns track the volatility-target baseline more closely, so the gap between them is measured more precisely. The gap itself barely changed, but it is now statistically significant on the S&P 500 and NASDAQ, **against** the HMM. The rule was fixed from training evidence before these results were seen, and kept. None of the differences is statistically significant either way.

**What no rule fixes:** Gold's *Crisis* regime lost money in training but earned about as much as its Bull regime out-of-sample. Its regimes simply did not carry over well from the training years, and fitting a rule to the test period to hide that would be exactly the overfitting this project avoids.

## 2. Core Concepts & Statistical Integrity

### A. Walk-forward training
The model is never fit on the full dataset. It uses an **expanding window refit once a year**: to predict year *Y*, the HMM and its `StandardScaler` are fit only on data before *Y*. The first prediction year is the first one with at least `min_train_days` (2,268 ≈ 9 years) of history before it.

Each fold is trained **from 5 random starting points** (`model.n_init`), and the one with the highest *training* log-likelihood is kept. EM only climbs to a nearby local optimum, and in most folds a later start beat the first one (by up to ~1,300 log-likelihood points), so a single start often settled for a poor fit.

### B. Filtered, not smoothed, probabilities
`hmmlearn`'s `predict()` (Viterbi) and `predict_proba()` (forward-backward) condition on the **whole** sequence passed in, so day 1's label would depend on day 250's data. `src/models/hmm.py::predict_proba_filtered` runs only the forward pass and normalizes it, which gives P(state at t | data up to t).

The forward pass runs **continuously over the full history** up to the end of each test year, and only the test-year rows are kept. Because row *t* depends only on rows 1..*t*, this adds no look-ahead. It just means the model's belief on 2 January carries over from 31 December instead of restarting every year. `tests/test_signal.py` checks the whole walk-forward is causal: deleting the last year of data leaves every earlier prediction unchanged.

### C. State labeling per fold
HMM state numbers are arbitrary and change on every refit. In each fold, states are labeled from their behaviour on **training data only** (`model.labeling`, rule `sharpe`):

- the state that **earned the most** (highest annualized Sharpe) → Bull, the one that **earned the least** → Crisis, so both always exist;
- every other state: Sharpe below −0.1 → Crisis; Sharpe above **both** 0.2 **and the asset's own Sharpe over the training years** → Bull; otherwise → Transition.

The rule went through three versions. Each was fixed from training-window diagnostics before its out-of-sample results were seen, and all three stay available in config so [Section 1](#what-steps-68-changed-one-change-at-a-time) can show results under each:

| Rule | Bull / Crisis anchors | Other states | Used in |
|---|---|---|---|
| `absolute` | calmest / most volatile | fixed bars: > 0.2 Bull, < −0.1 Crisis | Steps 1–5 |
| `relative` | calmest / most volatile | Bull only if better than holding the asset | Step 6 |
| `sharpe` | best-earning / worst-earning | Bull only if better than holding the asset | Step 7 (now) |

**Why judge against the asset itself:** a fixed bar of 0.2 means very different things for a flat asset and a strongly trending one. "Bull" should mean better than simply holding the asset; positive but worse than that is Transition.

**Why anchor on earnings, not calm (the Gold and Bitcoin investigation).** Under the first two rules Gold and Bitcoin never had a single Transition day. Fitting the model on their training windows showed why:

- *Gold:* the calmest state is a quiet drift that earns less than holding gold, while gold's rallies happen in a more volatile state. "Calmest = Bull" is true for stocks, where prices fall fast and rise slowly, but not for gold. The volatility anchor called that drift Bull just for being calm. Anchoring on earnings labels it Transition, and Gold now has a Transition regime. It came at a cost: the strategy now holds less gold during those quiet drifts, and gold kept rising through many of them, so Gold's HMM Sharpe went down (see [the comparison table](#what-steps-68-changed-one-change-at-a-time)). The rule was kept anyway, because switching back after seeing that result would be fitting the labels to the test period.
- *Bitcoin:* in every fold the four states are two rally states and two sell-off states. None is sideways, so no labeling rule can honestly produce a Transition regime. With 5 states a flat state appears in some training windows but not in others, so changing the number of states would not reliably fix it either. Bitcoin, as this model sees it, trends.

For stocks the best-earning state is also the calmest, and Bitcoin's anchors are the same under both rules, so switching to `sharpe` changed no label for the S&P 500, NASDAQ or Bitcoin. Only Gold's changed, on 565 out-of-sample days (checked against a run under the `relative` rule).

### D. One signal, defined once
`src/models/signal.py::compute_signal` is the **only** definition of the trading signal. The backtest, the SQLite store, the dashboard and paper trading all call it:

1. Take the filtered P(Bull), P(Transition), P(Crisis) for each day.
2. Smooth each with a **trailing 21-day mean** (`model.smoothing_window`), never a centered window, which would let future days into today's value.
3. **Regime** = the label with the highest smoothed probability.
4. **Target weight** = Σ smoothed P(regime) × the regime's weight, between 0 and 1. Each fold sets a regime's weight from its **training** window: 100% if the asset's mean return on that regime's training days was positive, 0% otherwise (`model.sizing: regime_returns`). In practice Bull is held, Crisis is not, and Transition is held only where it earned money in training.

Averaging probabilities, rather than taking the most common label, keeps the confidence information: a run of 51% Bull days and a run of 99% Bull days are not the same. `tests/test_signal.py` also checks that paper trading's path reproduces the backtest's probabilities exactly.

## 3. Evaluation Methodology

Implemented in `src/backtest/evaluation.py`.

1. **One window per asset.** The out-of-sample window starts on the first date with a real walk-forward prediction and ends on the last available date. Every strategy for that asset (HMM, buy-and-hold, 200-day MA, volatility target) is scored on exactly these dates.
2. **Signals may look back, P&L may not start early.** The 200-day MA on the first out-of-sample day uses the 200 days before it (that information was available then). But returns, costs and metrics are only counted inside the window.
3. **Everyone starts flat.** Each strategy enters the window with no position and pays the cost of its first trade.
4. **Same plumbing for everyone.** The same execution lag, cost model and metric functions apply to every strategy, so differences come from the signal alone.
5. **Per-asset annualization** from `config.yaml` (`backtest.annualization`): 252 rows per year for equities and gold, 365 for Bitcoin.
6. **One Sharpe definition.** Sharpe is measured on returns above the cash rate, and the same `compute_sharpe` is used for the results table and inside the significance tests.
7. **Signal from the index, P&L from what you can buy.** Signals use the index (long history, no fund fees); returns come from the traded instrument (`backtest.instruments`). The evaluation refuses to run if the instrument has no price for any day of the window, for example before the fund launched.

**The baselines** (`src/backtest/baselines.py`):

| Baseline | Rule |
|---|---|
| Buy & Hold | always 100% invested |
| 200-day MA | 100% when the index closes above its 200-day average, otherwise cash |
| Volatility target | invested `min(1, long-run average volatility / current 20-day volatility)`: fully invested at normal volatility, scaled down when volatility rises above its own history, never borrowing to go above 100%. Both volatilities use data up to the day only. |

The volatility target is the hardest baseline. The HMM mostly steps aside when markets get volatile, and a one-line volatility rule does the same with no model at all. If the HMM can't beat it, its regimes add nothing beyond "volatility is high".

## 4. Architecture & Data Flow

```text
[yfinance loader: indices, VIX, traded funds, T-bill rate] → [8 features] → [walk-forward HMM] → [labeling] → [signal] → [evaluation: HMM + 3 baselines on fund returns + cash, risk] → [regime analysis] → [portfolio (v2.0): equal weight, risk parity, regime-aware] → [significance] → [SQLite store + models/] → [Streamlit app / notebooks / README tables]
```

`src/pipeline.py::run_pipeline` runs all of it in one pass. Notebooks and `app.py` only **read** from `src/` and the store; they never recompute pipeline logic.

**One training run, two outputs.** Each run fits every walk-forward fold once and writes both the saved models and the database from that same fit. `--reuse-models` skips fitting and predicts with the saved folds instead: about 15 seconds instead of about 3.5 minutes, with identical results (tested in `tests/test_pipeline.py`). A retrain is required after any change to `config.yaml` or the features, and when a new calendar year starts; the pipeline refuses to reuse models in those cases.

**Crash-safe publishing.** Models are trained into a staging folder, and the database is built as a separate file. Only when every asset has succeeded are the new models, the manifest and the database swapped in, so the dashboard never sees a half-written result.

### Dashboard

`streamlit run app.py` opens an interactive Plotly dashboard with eight tabs. Everything on it is read from the SQLite store; the app never fits a model or recomputes a metric.

| Tab | What it shows |
|---|---|
| **Overview** | Today's regime, regime probabilities and target exposure for all four assets; a cross-asset scoreboard (Sharpe, CAGR, max drawdown vs both baselines); headline findings generated from the stored results; the forward test of every frozen version |
| **Regimes** | Price on a log scale shaded by regime, above the stacked regime probabilities (smoothed, or raw with a toggle); recent regime spells; time spent in each regime |
| **Performance** | Full metrics table; growth of $1, drawdown and rolling 1-year Sharpe for all three strategies; calendar-year returns; equity stress episodes |
| **Risk** | Historical VaR / CVaR and Cornish-Fisher VaR; how much each strategy was invested over time; turnover and total costs paid |
| **Model insight** | What each regime looked like (returns, volatility, average VIX / RSI / ADX); day-to-day transition probabilities; spell lengths; every yearly fold's HMM states and the labels they received |
| **Statistical evidence** | Sharpe differences vs each baseline with 95% bootstrap intervals; bootstrap, HAC and Holm-adjusted p-values |
| **Portfolio (v2.0)** | The pre-registered verdict and its rule word for word; the regime-aware portfolio vs equal weight and risk parity (table and significance tests); growth of $1, drawdown and rolling Sharpe; what each portfolio held through time |
| **Paper trading** | Latest signal, data and model freshness checks, how to run `scripts/paper_trade.py`, and its trade log |

Design notes:
- **Read-only.** The store is opened with SQLite's read-only mode and closed after each query, so the dashboard can't change results or block the pipeline from publishing a new database. Cached queries reload automatically when a new database appears.
- **Pinned to one run.** Every query is filtered to the latest `run_id`, so rows from different runs are never mixed.
- **Honest headlines.** The overview's summary sentences (e.g. on how many assets the HMM beat buy-and-hold, and whether any difference is significant) are computed from the store each time the page loads, never typed by hand.
- **Readable for everyone.** Colours follow the entity everywhere (each strategy and each regime has one fixed colour) and were checked with a colour-vision-deficiency validator in light and dark themes. Red-vs-green for Bull/Crisis was rejected because red-green colour-blind readers can't tell them apart. Regime names are always shown as text and symbols (▲ Bull, ◆ Transition, ▼ Crisis), never as colour alone. Charts never use two y-axes on one plot.
- **Tested.** `tests/test_dashboard.py` builds a small store with the real pipeline and runs the real `app.py` headlessly through every tab and asset.

## 5. Features (the 8 inputs)

Computed with the `ta` library and pandas. Every indicator uses only past and current rows, and warm-up rows are dropped, never back-filled.

**Every feature is scale-free**: multiplying all prices by 10 leaves every feature unchanged (`tests/test_features.py`). This matters because the scaler is fit on early years and applied to later ones.

| Group | Feature | Description |
|---|---|---|
| Momentum | `returns` | Daily % change |
| | `rsi` | 14-day Relative Strength Index (0–100) |
| Trend | `macd_pct` | MACD line (12/26) ÷ Close |
| | `adx` | 14-day Average Directional Index (trend strength, 0–100) |
| Volatility | `volatility_20` | 20-day rolling std of returns |
| | `atr_pct` | 14-day Average True Range ÷ Close |
| Volume / macro | `obv_flow_20` | 20-day signed volume ÷ 20-day total volume, in [−1, 1] |
| | `vix` | CBOE VIX close, forward-filled onto each asset's calendar |

**Why the change (Step 2):** the earlier `atr` and `macd` were in price points. Over the last 2 years the S&P 500's ATR averaged ~6.7 standard deviations above its 2000–09 training mean, simply because the index is several times higher, so the model saw "extreme volatility" every day. The earlier `obv_ratio` (OBV ÷ its EMA) reached values like +1,016 (NASDAQ) and −419 (Gold) when OBV crossed zero. `obv_flow_20` keeps the same idea (is volume backing the up-days or the down-days?) but stays between −1 and 1.

## 6. Backtest Realism

- **Execution lag:** a weight decided at day *t*'s close is traded at day *t+1*'s close and earns returns from day *t+2*. Tested in `tests/test_backtest.py`.
- **Tradable instruments:** P&L comes from SPY (S&P 500), ONEQ (NASDAQ Composite), GLD (gold) and spot BTC-USD, using adjusted prices so dividends and the funds' own fees are included (`backtest.instruments`). The signal still comes from the index. A fund's price is put onto the index's calendar by carrying the last known price forward, never a later one.
- **Interest on cash:** the uninvested share earns the 3-month T-bill yield (`^IRX`), using the rate known at the previous close. Without this, a strategy that is often in cash is charged 0% on that cash, which unfairly penalises it against buy-and-hold.
- **Transaction costs:** spread + commission per unit of turnover, set in `config.yaml` (`backtest.costs`): 1.5 bps for SPY, 3.5 bps for ONEQ (it trades far less than SPY), 2.5 bps for GLD, 5.5 bps for Bitcoin. `run_backtest` requires the cost explicitly, so no backtest can silently run cost-free.
- **Probability-weighted sizing:** HMM exposure = trailing 21-day mean of each regime's probability × that regime's training-based weight, between 0 and 1 (`src/models/signal.py`). An optional regime-aware volatility scaling (`model.vol_scaling`) multiplies this by the volatility baseline's rule; it is off by default. Positions under 0.1% of the portfolio are set to 0: nobody would trade them, and floating-point noise around such tiny weights made some metrics change between runs.
- **Risk reporting:** historical and Cornish-Fisher VaR, historical CVaR, drawdown depth and duration.

## 7. Limitations

| Limitation | Explanation |
|---|---|
| **Labels come from training returns** | Each fold's best-earning state is called Bull and its worst-earning state Crisis, judged on that fold's training data only. A state that earned well in training can behave differently out-of-sample (see the Gold row). |
| **Gaussian emissions** | `hmmlearn`'s Gaussian HMM assumes normal returns within each state. Real returns have fat tails. |
| **Detection lag** | The 21-day trailing smoothing delays reactions to regime changes. In the S&P 500 stress episodes the smoothed regime left Bull 13–36 trading days after the peak (it was already Transition at the 2011 peak), when buy-and-hold (SPY) had already lost between 0.8% and 18.9%. Since Step 8 the strategy also holds Transition where it earned money in training, so its exposure only drops below 50% once Crisis dominates: 13–97 trading days after the peak in five episodes, and not during the 2015–16 sell-off at all (notebook 03). That is the cost side of the Step 8 sizing. |
| **Labeling thresholds are judgement calls** | The Sharpe bars (0.2, −0.1, and the asset's own training Sharpe) are reasonable but not estimated. Section 1 shows how much the switch from the fixed to the relative rule moved the results. |
| **No Transition regime for Bitcoin** | In every fold its four HMM states are two rally states and two sell-off states, so no labeling rule produces a sideways regime (see [Section 2C](#c-state-labeling-per-fold)). A training-only probe found a flat state in at most 2 of 6 yearly windows with 4 or 5 states, and in 4 of 6 only with 6 states; dropping VIX made it worse. A 6-state Bitcoin model is available as an option (`model.n_states_by_asset`) but not used by default: one model size for every asset is less prone to overfitting. |
| **Gold's regimes don't carry over well** | Gold's Crisis regime lost money in training but earned about as much as Bull out-of-sample, so stepping out of it cost return. No training-based rule can anticipate that. |
| **Stress-episode dates are equity-based** | The episodes are S&P 500 peak-to-trough windows applied to every asset, which shows how Gold and Bitcoin behaved during *equity* stress, not during their own crashes. |
| **Fund proxies and the cash rate** | The signal comes from the index but P&L from a fund, so a gap between the two (tracking error) is part of the result. ONEQ is thinly traded, so its 3 bps spread is an estimate. `^IRX` is a discount yield, used as a close approximation of what idle cash earns. Bitcoin is traded spot, with no ETF fees but exchange fees folded into its 5 bps spread. |
| **Yahoo revises adjusted prices** | Yahoo recalculates dividend-adjusted fund prices from time to time. Two downloads a day apart differed by at most 1.8e-6 in a daily SPY or ONEQ return, which moved Sharpe ratios and other metrics by at most 4e-5 (4th–5th decimal). Regimes, positions and trades were identical, because the signal comes from the index, not the fund. A rerun on a later download can therefore differ from the stored numbers in the last decimals; this is expected and harmless. |
| **Private `hmmlearn` API** | Filtered probabilities use `hmmlearn._hmmc.forward_log`, so `hmmlearn` is pinned to `>=0.3,<0.4`. |
| **Number of states** | BIC on the first training window keeps falling up to 6 states (notebook 02). Four states are used because each can be mapped to an economic regime; this is a judgement call, not a statistical optimum. |

## 8. How to Run Locally

Requires **Python 3.10–3.12**. `requirements.txt` pins `numpy<2.0`, which has no wheels for 3.13.

```bash
git clone https://github.com/Anshuman0716/Stock-Market-Regime-Prediction.git
cd Stock-Market-Regime-Prediction

python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # Mac / Linux
pip install -r requirements.txt               # or requirements-dev.txt for notebooks + lint

python scripts/run_pipeline.py                 # train + evaluate + write the store (~3.5 min)
python scripts/run_pipeline.py --reuse-models  # daily refresh with saved models (~15 s)
python scripts/forward_test.py                 # results since the v1.0 freeze
pytest                                         # test suite
streamlit run app.py                           # dashboard at http://localhost:8501
```

```bash
ruff check .                                   # lint (settings in ruff.toml)
pytest                                         # tests
jupyter nbconvert --to notebook --execute --inplace notebooks/*.ipynb   # re-run the notebooks
```

On Windows, `run_all.bat` does all of this with [uv](https://docs.astral.sh/uv/) on Python 3.12.
